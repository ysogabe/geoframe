# FIXTURES.md --- GeoFrame サーバ応答の fixture

`native-display/` は GeoFrame サーバ（`app/`・Python）に HTTP で繋がる C++
クライアントである。ネットワークに依存しないテストを書くため、**実サーバの本物の
レスポンス**を採取して fixture にしてある。

採取スクリプト: [`tools/capture-fixtures.sh`](../tools/capture-fixtures.sh)

---

## 1. 2系統の fixture

| | 置き場所 | git | 内容 |
|---|---|---|---|
| **コミット版** | `assets/fixtures/` | **追跡する** | 件数を絞り、**位置情報をすべて合成値へ置換**したもの |

（テストが実データと違う形を見ることになるため）。変えたのは**値だけ**。

## 3. コミット版で何を合成値に置き換えたか

再現できるよう、**置換はすべて `tools/capture-fixtures.sh` の中に実装**してある
（手作業ではない）。何をしたかの記録は `assets/fixtures/index.json` の `synthesis`
にもある。

### 3-0. 方針と、前の方式が破られた経緯

**fixture の目的は「構造とパターンの多様性」を再現することであり、地名や座標の
実在性は要件ではない。** よって位置を示す情報はすべて合成値に差し替える。

以前の版は「座標を小数第2位に丸めてから固定オフセットを足す」方式だった。
これはセキュリティレビューで**実測で破られた**。記録として残す:

1. **オフセット値がこの文書と `index.json` にそのまま書かれていた。** 減算すれば
   元座標が約1km粒度で復元でき、**50/50件すべてで復元が成立した**。
2. **オフセットを消しても解決しなかった。** 位置を示す情報が座標以外にも無加工で
   残っていたため --- `trips[].label`（市区町村名＋年月）、`top_cities`、`pref_list`、
   各レコードの `pref` / `city` / `place` / `title` / `elev`。
3. これらの**組み合わせ**（1km升目 ＋ 大字レベルの地名 ＋ 日付 ＋ 標高）から、
   数年分の実移動履歴が再構成できた。

前の版の §3-4 は「地名は座標がぼけているから残してよい」「座標は地名があるから
粗くてよい」と互いを根拠にする**循環論法**だった。特定を可能にしたのは
**両者の組み合わせ**であり、片方ずつ見て安全と判断したのが誤りだった。

### 3-1. 緯度・経度

対象は `api/photos.json` の `lat`/`lon`、`api/admin-photos.json` の `lat`/`lon`、
`api/stats.json` の `trips[].bounds`。

**合成座標は実座標を一度も読まずに生成している。** 実座標に何かを足す・引く・
丸めるといった変換は**一切していない**。差分や回帰で元に戻せる余地を残さないため。

生成の手順:

```
県の中心   = 日本の緯度経度の範囲内の一点（「県の索引」から決定的に生成）
市の中心   = 県の中心 + 市オフセット（「市の索引」から生成）
大字の中心 = 市の中心 + 大字オフセット（「大字の索引」から生成）
写真の座標 = 大字の中心 + 写真ごとの微小なゆらぎ（写真 id から生成）
```

- **入力は索引と写真 id だけ**で、実際の緯度経度も実際の地名の文字列も入らない。
- 階層構造にしてあるので「同じ地名なら近くに集まる」性質は実データと同じ。
  地図描画・グループ化のテストが不自然にならない。
- 逆ジオコーディングが失敗した写真（`pref`/`city`/`place` が空）は地名から座標を
  決められないので、**同じ `trip` の中で最初に地名が取れた写真の周り**に置く。
  こうしないと `trip` の `bounds` が日本中に広がってしまう。

### 3-2. 地名・タイトル

| フィールド | 置換後 |
|---|---|
| `pref` | `A県` / `B県` / … |
| `city` | `A市` / `B市` / … |
| `place` | `A町` / `B町` / … |
| `trips[].label` | `YYYY.MM A市の旅`（年月・地名とも合成値） |
| `top_cities` / `pref_list` | 上と同じ置換表を通すので**架空地名と整合する** |
| `title` | 架空の値（下記） |
| `env.weather` / `weekly` / `quakes` | 同じキーと型を持つ合成データ |

**同じ元値は必ず同じ置換値になる。** 一貫性が壊れるとグループ化のテストが
無意味になるため。空文字列は空文字列のまま残す（「地名が取れなかった」分岐は
テスト対象なので潰してはいけない）。

> #### ⚠️ 置換の索引は「元データ内での初出順」で振ること
>
> **元の文字列をハッシュしたり辞書順に並べたりして索引を作ってはいけない。**
> 都道府県は47・市区町村は約1900しか候補が無いので、置換値が元の文字列の関数に
> なっていると、候補を総当たりして同じ関数を計算するだけで逆引きできてしまう。
> 初出順は元データ（`tests/data/`）が無ければ再現できないので逆引きできない。
>
> 生成に使う固定シードは**公開して構わない**。合成値は「索引」の関数であって
> 「元の値」の関数ではないので、シードから分かるのは索引→合成値だけであり、
> 索引→元の値は分からない。

`title` の作り方は元の系統で分ける。実データのタイトルは次の3系統だった
（`title` が日本語かどうかは `place` が空かどうかと完全に一致する）:

| 元の系統 | 件数 | 置換方法 |
|---|---|---|
| カメラ既定のファイル名（純 ASCII・8文字） | 836 | **文字数をそのまま保つ**。位置情報を含まないため |
| UUID 形式（純 ASCII・36文字） | 2 | 区切り位置と文字数だけ保つ |
| 地名を含む日本語タイトル | 969 | 架空の地名＋架空の語。**文字数は元から取らない** |

日本語タイトルの**文字数を保ってはいけない**。地名を含むので、文字数を保つと
「実在の地名の文字数の分布」が漏れ、市区町村リストと突き合わせられてしまう
（§3-0 の「組み合わせで破られる」のと同じ形）。長さは合成後の索引と写真 id から
決めており、結果として 5〜18文字の幅が出るので表示幅・省略のテストには使える。

### 3-3. 標高（`elev`）

合成値。**`null` と数値の分岐は保つ**（実データでは `place` が空のとき `null`）。
小数第1位までという実データの形式も保つ。

> この項目は前回のレビューで「意図的に残したものリストから漏れていた見落とし」と
> 指摘された。標高は 1km 升目の中で高さを1桁まで特定できるので、地名・日付と
> 組み合わさると強い手がかりになる。

### 3-4. ファイル名・識別子

| フィールド | 置換後 | 理由 |
|---|---|---|
| `photos[].file` | `derivatives/fixture-0001.jpg` | 元の値は Google Drive のファイルIDを含む |
| `admin-photos.items[].thumb` | `/derivatives/fixture-0001.jpg` | 同上 |
| `admin-photos.items[].name` | `FIXTURE_0001.JPG` | 元のカメラのファイル名 |

**先頭スラッシュの有無は元の非対称のまま保存している**（§5 の落とし穴を参照）。
`photos[].file` は**スラッシュ無し**、`admin-photos.items[].thumb` は**スラッシュ有り**。

### 3-5. 日時・室内環境・在室情報

- **撮影日時・取得日時**は、実際の値と間隔を使わず、固定基準日から一定間隔で生成する。
  文字列表現と並び順を維持するため、日時解析や時系列処理のテストには利用できる。
- **旅の開始日・終了日・年月・月別件数**も合成した撮影日時から再計算する。
- **室内環境**はセンサー名、entity ID、実測値、更新時刻を合成値へ置換する。
- **在室情報**は更新時刻を合成値へ置換する。状態値はUIの分岐テスト用に残す。

以下は利用者の個人情報と結びつかない公開情報または集計値として残している。

- **集計値（`stats.total` / `pref_count` / `dist_km` / `inferred` / `pending`、
  `trips[].count`、`top_cities` の枚数）**

### 3-6. 件数の絞り方

`photos.json` は元データから50件へ縮小する。**乱数を使わない決定的な選び方**で、テストの分岐に
効く多様性を確保している:

1. まず必須パターンを1件ずつ確保 --- `inferred` の true/false、`elev` の null/数値、
   `place` の空/非空、`city` の空/非空、`fav` の true/false
2. 残りは `pref` ごとのグループを round-robin で巡回（地域の偏りを防ぐ）
3. 最後に元の並び順（撮影時刻順）に戻す --- `trip` の割り当てが時系列前提のため

生成結果の件数と分岐網羅は、再生成後にテストで確認する。

### 3-7. 検証（`tools/capture-fixtures.sh` 実行後に必ず確認すること）

| 確認項目 | 実測結果 |
|---|---|
| コミット版の座標がフル版の座標と一致する件数（6桁・2桁とも） | **0件** |
| 合成座標とフル版座標の差分が一定（＝オフセット方式）か | **相異なる差分 50/50**。一定ではない |
| 合成座標からフル版座標への最小二乗逆推定の残差 | **lat 426km / lon 351km**（元の散らばりの 97% / 91% が残る＝復元不能） |
| フル版から抽出した実地名・実タイトル 1000件超が、コミット版の全ファイルに現れる件数 | **0件** |
| キーの集合と順序がフル版と一致するか | 全ファイルで一致 |
| `null` / 空 / 型の分岐がフル版と同じか | 一致 |
| `trips[].bounds` が合成座標と整合するか | 全 trip で `w<e` / `s<n`、抜粋50件すべてが自 trip の `bounds` 内 |

## 4. 合成データ --- 注入用の地震（`quakes-inject.json`）

> **このファイルは実データではない。** 実測した quake の**構造だけ**を借り、
> 震度・時刻・場所を人手で差し替えた**合成データ**である。

実データの `quakes` には震度3以上がめったに現れない（採取時の実データは 10件すべてが
`maxi` = `"1"` か `"2"` だった）。「震度3以上でアラートを出す」ロジックはそのままでは
テストできないため、この fixture を用意した。

**`eid` はすべて `FIXTURE-` 始まり**。実データの `eid` は `"20260730135103"` のような
14桁の数字なので、**実データと取り違えようがない**。

ファイル全体は `/api/env` と**完全に同じ形**（`weather` / `weekly` / `quakes`）なので、
`/api/env` の応答としてまるごと差し込める。`weather` が `null`・`weekly` が空なのは
サーバ側で実際に起こりうる状態（気象庁の取得失敗時）であり、その経路も同時に踏める。

含まれる 13件のバリエーション:

| `eid` | `maxi` | 狙い |
|---|---|---|
| `FIXTURE-0001` | `"1"` | 閾値未満 |
| `FIXTURE-0002` | `"2"` | **閾値未満 --- アラートを出してはいけない** |
| `FIXTURE-0003` | `"3"` | **閾値ちょうど --- 出す** |
| `FIXTURE-0004` | `"4"` | 閾値超 |
| `FIXTURE-0005` | `"5-"` | **`std::stoi` で解析できない表記** |
| `FIXTURE-0006` | `"5+"` | **同上** |
| `FIXTURE-0007` / `0008` | `"6-"` / `"6+"` | 同系統の表記 |
| `FIXTURE-0009` | `"7"` | 最大 |
| `FIXTURE-0010` / `0011` | `"3"` | **`time` がどちらも `"23:50"` で `at` の日付だけ違う** |
| `FIXTURE-0012` × 2 | `"3"` | **同一 `eid` の重複** |

## 5. 実測して分かったレスポンスの落とし穴

次フェーズのクライアントを書く前に必ず目を通すこと。すべて**このサーバで実測**した。

### 5-1. `/api/photos` は裸の JSON 配列

`{"items": [...]}` では**ない**。トップレベルがいきなり `[` で始まる。

```json
[{"id": 1, "fetched_at": "...", "fav": false, "file": "...", ...}, ...]
```

### 5-2. `/api/env` と `/api/stats` に `ok` フィールドが無い

実測（`tests/data/*.body` で確認）:

| エンドポイント | `ok` |
|---|---|
| `/api/env` | **無し**（トップレベルは `quakes` / `weather` / `weekly` の3つだけ） |
| `/api/stats` | **無し**（`total` / `pref_count` / … ） |
| `/api/presence` | **無し** |
| `/api/photos` | **無し**（そもそも配列） |
| `/api/roomenv` | **有り** |
| `/api/admin/photos` | **有り** |

**`ok` の有無でエンドポイントごとに非対称**。共通の「`ok` を見て成否を判定する」
ヘルパを書くと `/api/env` と `/api/stats` で必ず落ちる。

### 5-3. `roomenv` の `value` は常に文字列

```json
{"entity": "sensor.…_temperature", "value": "23.83", "unit": "°C", ...}
```

`23.83` ではなく `"23.83"`。二酸化炭素の `"9454"` も文字列。数値として扱うなら
クライアント側で変換が要る。

### 5-4. `presence.night` は3値

`true` / `false` / **`null`** をとる。`null` は「Home Assistant 未設定・取得失敗」を
意味し、`false`（＝日の出後）とは**意味が違う**。bool に潰してはいけない。
3値それぞれの fixture を `api/presence-night-*.json` に用意してある。

### 5-5. エラーが HTML で返る経路がある ← 最重要

**このサーバはエラーを JSON で返すとは限らない。** 以下はすべて `text/html;charset=utf-8`
で、Python 標準の `SimpleHTTPRequestHandler` が生成する HTML エラーページを返す:

- Host 検証で拒否された **403**
- 静的ファイルのホワイトリスト外 **403**
- **404**

```
HTTP/1.0 403 Forbidden host
Content-Type: text/html;charset=utf-8

<!DOCTYPE HTML>
<html lang="en">
  …<p>Error code: 403</p>…
```

**「どんな応答でも JSON parse する」クライアントは、最も診断が必要な場面でクラッシュする。**
必ず**ステータスコードを先に見て**から本文を扱うこと。採取スクリプト自身もこの原則で
書いてある。

### 5-6. `maxi` に `"5-"` `"5+"` がある

震度は `"5-"`（5弱）・`"5+"`（5強）という表記をとる。`"6-"` `"6+"` も同様。
**`std::stoi` では解析できない**（`std::stoi("5-")` は `5` を返して `-` を黙って捨てる
ため、5弱と5強の区別が消える）。文字列として比較するか、専用のパーサを書くこと。

### 5-7. `time` は `"HH:MM"` で日付が落ちている

```json
{"time": "13:51", "at": "2026-07-30T13:51:00+09:00"}
```

`time` は5文字しかなく**日付情報が無い**。日をまたぐと衝突するので、
**同定・重複判定には `at`（ISO8601・タイムゾーン付き）を使うこと**。
`quakes-inject.json` の `FIXTURE-0010` / `FIXTURE-0011` がこの衝突を再現している。

### 5-8. `file` と `thumb` で先頭スラッシュが非対称

| API | フィールド | 値 |
|---|---|---|
| `/api/photos` | `file` | `derivatives/….jpg` --- **先頭スラッシュ無し** |
| `/api/admin/photos` | `thumb` | `/derivatives/….jpg` --- **先頭スラッシュ有り** |

URL を組み立てるとき、片方に合わせると他方で `//` や欠落が起きる。
どちらを扱っているか意識すること。この非対称は fixture でもそのまま保存してある。

## 6. 再採取のしかた

### 6-1. サーバを採取用ポートで起動する

> **ポート 8080 では別のサーバが動いていることがある。これは停止しないこと。**

```bash
cd <repo>/app
source .venv/bin/activate
GEOFRAME_PORT=8099 GEOFRAME_DRIVE_KEY=/nonexistent-disable-sync.json python server.py
```

- `GEOFRAME_DRIVE_KEY` を**存在しないパス**にすると Drive 同期ワーカーが起動しない。
  `catalog.db` は**読むだけ**になるので、既存サーバと同時に起動しても書き込み競合しない。
- `.venv` と `catalog.db` は**メインのワークツリーにしか無い**（どちらも `.gitignore`
  済みのため git worktree 側には存在しない）。必ずメインツリーのパスで起動すること。
- 起動には少し時間がかかる。疎通するまで待つこと。

### 6-2. 採取する

```bash
cd <repo>/native-display
tools/capture-fixtures.sh          # 既定ポート 8099
tools/capture-fixtures.sh 8099     # 明示
GEOFRAME_FIXTURE_PORT=8099 tools/capture-fixtures.sh
```

スクリプトは**サーバを起動しない**（誤って本番の 8080 を触る事故を避けるため）。
繋がらないときは起動方法を案内して `exit 1` する。

**冪等**。同じ入力に対する変換は決定的（乱数を使わない）ので、再実行しても
出力を上書きするだけ。実データ側が変わった分と `Date:` ヘッダ以外に差分は出ない。

### 6-3. 採取後に必ず確認すること

```bash
git status --short              # tests/data/ が現れないこと
git check-ignore -v native-display/tests/data/photos.body
```

**フル版が追跡対象に入っていないことを、目視で確認すること。**
実座標が一度コミットされると履歴から消すのが面倒になる。

### 6-4. 終わったらサーバを止める

採取用に起動した 8099 のプロセスは停止する。**8080 のサーバには触らないこと。**
