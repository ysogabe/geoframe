# 写真ライブラリと選別の確認（B） PRD

作成日: 2026-11-01。状態: 設計レビュー 2 回（Sol）・安全面レビュー 2 回（Opus）を反映済み。ユーザー承認待ち。

## 背景と目的

[ADR 0008](../decisions/0008-photo-platform-and-miharashi-display.md) で geoframe は写真管理基盤になり、
表示は miharashi に移った。管理画面は [A: 整え直し](../admin-rework/prd.md)（PR #70・#71・#72、2026-11-01 に
本番配布済み）で「状況 / 写真 / 設定」の 3 タブになったが、A の「やらないこと」に書いた次の 2 つが残っている。

- **G3 写真ライブラリ**: 写真を旅・地図（・日付・場所）で眺める画面。今の「写真」タブは撮影日時順の
  1 本の一覧と絞り込みだけで、約 6,500 枚から「あの旅の写真」「この辺りで撮った写真」にたどり着けない。
- **G4 選別の確認**: 品質解析（`quality-scan`）が exact / similar のグループごとに決めた推奨
  （miharashi が `quality_recommended` で読む）を、人が確かめて別の写真に変えられる画面と API。今は推奨を見る
  場所も変える手段も無く、気に入らないときは写真を「除外」するしかない。

本 PRD は B として、この 2 つと、両方の前提になる**一覧用のサムネイル**を定める。
運用コンソール（C: sync・quality-scan・AI ジョブの操作）は引き続き範囲外。

## 使う人と場面

- 作者 1 人が、家庭 LAN 内のブラウザから使う。認証は無い（外部公開時は Cloudflare Access）。
- 場面:
  (a) 旅の後に、その旅の写真をまとめて見返し、位置なしの写真や向きの違う写真に気づいて直す。
  (b) 地図で「この辺りの写真」を探す。位置の付け間違いを見つける。
  (c) 似た写真の組を見て、miharashi に出す代表を自分で選ぶ。確認が済んだ組を再び見なくて済むようにする。
  (d) 組に新しい写真が増えたり原本が変わったりしたとき、その組だけもう一度見る。

## ゴール / やらないこと

ゴール:

- 「ライブラリ」タブで、旅ごと・地図上の 2 つの眺め方ができ、どちらからも拡大表示と ★・除外ができる。
- 「選別」タブで、品質解析のグループを 1 組ずつ並べて見て、代表を選び直すか、そのまま確認済みにできる。
  人の選択は `quality-scan` を再実行しても消えず、miharashi のフィードの `quality_recommended` に反映される。
- 一覧用の小さなサムネイルを配り、ライブラリと選別の一覧が表示用画像（長辺 2,560px）を読まずに済む。

やらないこと:

- 旧 AI の同一場面判定（`photo_ai_groups`）と新しい場面の判定（`ai_scene_*`）の確認（2026-11-01 のユーザーの決定。
  G4 は品質解析のグループだけ）。
- 代表以外を自動で除外すること（決定: 除外は今までどおり 1 枚ずつ「除外」ボタンで行う）。
- 品質解析の再実行、サムネイルの一括生成の操作、同期の操作（C の範囲）。
- 写真の削除・移動、Drive への書き戻し、原本の編集。
- 旅の名前付け・結合・分割。旅はフィードと同じ 48 時間超の間隔の区切りで機械的に決める。
- 表示（スライドショー等）の機能。ライブラリは管理のための一覧で、miharashi の表示を置き換えない。
- `GET /api/v1/photos` の**項目と形**の変更。`quality_recommended` の**値**が人の選択を反映するようになるのは
  意図した変更で、契約の文書を直す（R19）。
- フレームワークやビルド工程の導入。素の JavaScript を続ける。地図は同梱済みの MapLibre を使う。
- 本番への反映。マージまでが範囲で、本番の更新はユーザーの立ち会いで別途行う。

## 要求

### サムネイル

- R1（必須）: 写真 ID で引ける小さなサムネイル（長辺 320px の JPEG）を `GET /thumb/<id>.jpg` で配る。元は表示用画像
  （`display`。無ければ Drive の表示用 derivative）。URL の版が今の世代と一致し、書き込み側のある起動のとき、初回の要求で
  作ってデータディレクトリの `thumbs/` に置き、2 回目からはファイルを返す。元の写真が変わる（回転・原本の更新）と作り直す。
- R2（必須）: サムネイルの URL は版（元の写真の世代）を含む形で API が返し、ブラウザが長く（1 日以上）キャッシュして
  よい。`/derivatives/` と `/photos/` の配信とヘッダは変えない。
- R3（必須）: 作れないときの扱いを決める。表示用画像が無い・復号できない・大きすぎる写真は 404 で、画面は「画像なし」の
  代わりの表示にする。作れたが `thumbs/` に書けないとき（と、書き込み側の無い起動）は元の表示用画像を返す。同時に作る数と
  待ち（時間・数）に上限を設け、超えたら 503 を返して画面は「画像なし」にする。復号できない・大きすぎる写真（同じ世代）は
  件数に上限のある記憶に入れ、記憶にあるあいだは作り直さない。書き込みの失敗はしばらく置いて再試行する。
  表示用画像の作成より厳しい復号の上限を置き、全体を復号する前に断る。
- R4（あると良い）: 「写真」タブのカードの画像もサムネイルにする（カードの見た目と試験は変えない）。

### ライブラリ（G3）

- R5（必須）: ヘッダに「ライブラリ」タブを足す（並びは 状況 / 写真 / ライブラリ / 選別 / 設定）。タブの中に
  「旅 / 地図」の切り替えを置く。
- R6（必須）**旅**: 撮影日時のある全写真（除外を含むかは切り替え、既定は含まない）を 48 時間超の間隔で区切った
  旅の一覧を、新しい順に出す。各旅に、期間、枚数、位置なしの枚数、主な場所（都道府県・市区町村の上位 3 つ）、
  表紙のサムネイル。旅を選ぶと、その旅の写真をサムネイルの格子で撮影順に出す（ページあり）。撮影日時の無い写真は
  末尾に「日時なし」としてまとめる。
- R7（必須）**地図**: タブいっぱいの地図に、位置のある写真を点で出す。近い点はまとめて件数で出し（クラスタ）、
  押すと寄る。点を押すとサムネイルと撮影日時・地名が出て、そこから拡大表示へ進める。「今の表示範囲の写真を見る」で、
  範囲内の写真を R6 と同じ格子で出す。旅の一覧から「地図で見る」でその旅の期間に絞れる。
- R8（必須）: 格子・地図のどちらからも、写真を押すと「写真」タブと同じビューア（拡大・前後移動・★・除外）が開く。
  ★・除外の変更は、同じ写真を出している格子・カード・ビューアのすべてに反映され、「写真」タブの一覧の別の写真を
  変えない。画像が読めないときは「画像なし」の代わりの表示にする。
- R9（あると良い）**日付**: 年 → 月の件数つき階層で絞り込み、R6 と同じ格子で出す。
- R10（あると良い）**場所**: 都道府県 → 市区町村の件数つき階層で絞り込み、R6 と同じ格子で出す。国外（`pref` が空）は
  「海外・不明」にまとめる。
- R11（あると良い）: 格子の写真から「位置を指定」（今の位置指定モーダル）を開ける。

### 選別の確認（G4）

- R12（必須）: ヘッダに「選別」タブを足す。品質解析（`photo_quality`。今の写真と世代が合う行だけ）の 2 枚以上の
  グループを 1 組 1 段で出す。絞り込みは「未確認 / 確認済み / すべて」と「exact / similar / すべて」。各段には
  種類、枚数、撮影日時、状態（未確認・確認済み・再確認）と、メンバーのサムネイル（順位順）、各メンバーの点数・
  理由・懸念・★・除外・推奨（解析の推奨と、人が選んだ代表を区別して出す）。メンバーを押すと R8 のビューアが開く。
- R13（必須）: 各段で次の操作ができる。
  - 「この写真を代表にする」: 1 枚以上を選んで確定する（枚数の上限は設けない）。確定後、そのグループの `quality_recommended` は人が選んだ
    写真だけが `true` になる（解析の推奨は使わない）。グループは確認済みになる。
  - 「このままで確認済み」: 今の推奨（人の代表があればそれ、無ければ解析の推奨）を変えずに確認済みにする。
  - 代表に選べるのは、フィードに出せる写真（除外でなく、位置がある）だけ。選べない写真はサーバーが 400 で断り、画面でも
    選択肢にしない（今の解析の推奨も同じ穴を持つが、人が選ぶ場面では防ぐ）。
  - 「取り消す」: 人の記録を消し、解析の推奨に戻す。グループは未確認に戻る。
- R14（必須）: 人の記録は専用の表に写真ごとに持ち、`quality-scan` の再構築（`photo_quality` の全行の入れ替え、
  `group_id` の振り直し）で消えない。記録には写真の世代（表示用画像のパス・原本の MD5 と更新時刻・内容のハッシュ。
  品質解析と同じ照合）を付け、写真が変わった（回転・原本の更新）記録は無効になる。
- R15（必須）: 確認済みのグループに新しい写真が加わった、または記録が無効になったメンバーがいるときは、状態を
  「再確認」として未確認と同じ絞り込みに出す。
- R16（必須）: 確定・取り消しは、画面が見たメンバーの集合と内容（サーバーが出す印）が今のグループと一致するときだけ
  受け付ける。一致しない（再構築で組み替わった・写真が変わった）ときは 409 を返し、画面は「組が変わりました」と出して
  その段を読み直す。グループの枚数に上限を設けない。
- R17（必須）: `GET /api/v1/photos` の `quality_recommended` と、exact グループの推奨外を落とす条件は、人の選択を
  反映した推奨で決める。旧 AI の同一場面の抑止は、人が代表に選んだ写真を（お気に入りと同じく）落とさない。それ以外の
  項目・並び・除外条件は変えない。
- R18（あると良い）: 状況タブに「未確認・再確認のグループ数」を出し、押すと選別タブに移る。
- R19（必須）: [写真フィードの契約](../architecture/photo-feed-contract.md) と `photo-feed.schema.json` の
  `quality_recommended` の説明文に「管理画面で人が代表に選んだ写真があるグループでは、その写真だけが `true`」を書き足す。
  型・必須の項目・miharashi は変えない。状況タブの `db.quality` の `recommended`・`exact_suppressed` も人の選択を反映した
  値にする（人の記録が無ければ今と同じ値）。

### 安全・互換

- R20（必須）: 認証が無い前提の防御（Host 検査、JSON の Content-Type と Origin による CSRF 対策、POST の 64 KiB 上限、
  `INGEST=0` での書き込み API の 503、未知の POST の 403）を変えず、新しい書き込み API も同じ経路を通す。新しい
  JSON の読み取り API は GET のみで `Cache-Control: no-store`。画像の `/thumb/` は既存の画像の配信に合わせて HEAD も受けるが
  生成はせず、成功のキャッシュだけ R2 の長いキャッシュを例外にする。
  `/thumb/` の生成は、URL の版が今の世代と一致するときだけ行い、別のサイトのページから（`<img>` の連番で）起こせない
  ようにする。書き込み側の無い起動（`INGEST=0`）では生成しない。
- R21（必須）: `/thumb/<id>.jpg` は数字の ID だけを受け、読む元ファイルと返すファイルは `derivatives/`・`photos/`・`thumbs/`
  の領域の中に限る（`/derivatives/` と同じ正規化と検査。DB の `display` が外を指していても返さない）。クライアントが
  パスを指定する余地を作らない。サムネイルの生成に使う CPU・メモリには表示用画像の作成より厳しい上限を置く。
- R22（必須）: 既存の `GET /api/admin/photos`・`/api/admin/status` の形は、Python 版との完全一致の試験
  （`tests/admin_api.rs`）が通る範囲でしか変えない（新しい項目は新しい API に置く）。
- R23（必須）: 新しい表が無い DB（`INGEST=0` の読み取り専用の起動）でも、フィードと管理 API は今までどおり動く
  （人の記録が無いものとして扱う）。
- R24（必須）: `cargo fmt --check`・`cargo clippy --all-targets -- -D warnings`・`cargo test`（Node の描画試験を含む）が通る。
  JS は `innerHTML` 等で HTML を文字列から組み立てない決まりを守る。

## 受け入れ条件

- AC1（R1〜R3, R21）: 結合試験で、合成の表示用画像を持つ写真に `GET /thumb/<id>.jpg` が 200 `image/jpeg` を返し、長辺が
  320px 以下、`thumbs/` にファイルができ、`ETag` が付き、同じ `If-None-Match` で 304。表示用画像を差し替える
  （`display`・`mtime` を変える）と版が変わりサムネイルが作り直され、古い版のファイルが消える。表示用画像の無い写真は
  404、数字でない ID は 404、領域の外を指すリンクは 403。壊れた画像と寸法だけ大きい画像は 404 で、2 回目は生成を試みない
  （生成の回数を数える）。`thumbs/` に書けないときは元の表示用画像が返る。版が今の世代と違う要求と `INGEST=0` の起動では
  生成しない。同じ写真への同時の要求で生成は 1 回。`/derivatives/<id>.jpg` の応答ヘッダは変わらない
  （既存の試験）。
- AC2（R5, R6, R8）: 結合試験で `GET /api/admin/library/trips` が、合成 DB の写真（時刻差 10 分・1 時間 30 分・8 時間・
  9 日・ちょうど 48 時間）を、48 時間超の空きだけで区切る（ちょうど 48 時間は同じ旅、位置なしの写真も数える）。
  描画試験で旅の一覧に期間・枚数・位置なし・場所・表紙が描かれ、旅を押すと格子が出て、格子の写真を押すとビューアが
  開き、ビューアの ★ で `POST /api/admin/setflag` がその写真の `id` で呼ばれ、格子のタイルが更新され、「写真」タブの
  一覧の写真は変わらない。
- AC3（R7）: 結合試験で `GET /api/admin/library/points` が位置のある写真だけを GeoJSON で返し、`from`/`to` で絞れ、
  上限を超えると `truncated: true`。`bbox` 付きの `GET /api/admin/library/photos` が範囲内の写真だけを返す。描画試験で
  地図の source にその GeoJSON が渡り、「表示範囲の写真を見る」で `bbox` 付きの要求が出る（MapLibre は偽物に差し替える）。
- AC4（R12, R13, R14）: 結合試験で、exact 1 組・similar 2 組の合成 DB に対し `GET /api/admin/curation/groups` が 3 組を
  返し、`POST /api/admin/curation/confirm` で代表を変えると、(i) 応答と次の `groups` で人の代表と状態 `confirmed` が
  出る、(ii) `GET /api/v1/photos` の `quality_recommended` がその写真だけ `true` になり、exact グループでは選んだ写真だけが
  一覧に出る、(iii) `photo_quality` を全削除して解析結果を入れ直しても（`group_id` を変えても）(i)(ii) が保たれる、
  (iv) `GET /api/admin/status` の `db.quality.recommended` が (ii) と同じ数になる。
  「このままで確認済み」は推奨を変えずに `confirmed`（人の代表がある組ではその代表のまま）、「取り消す」で解析の推奨と
  `unconfirmed` に戻る。除外か位置なしの写真を代表にする `confirm` は 400 `representative_not_visible` で何も書かない。
- AC5（R12, R15, R16）: 結合試験で、確認済みのグループに写真を 1 枚足すと状態が `recheck` になり `state=unconfirmed` の
  絞り込みに出る。メンバーの世代を変える（再解析後を模す）と同様で、そのメンバーの記録は `stale`。印（`token`）が違う
  `confirm`・`reset` は 409 `group_changed` で何も書かない。描画試験で段（種類・枚数・状態・メンバー・点数・タグ）が
  描かれ、チェックして「代表にする」で `confirm` が `token` 付きで呼ばれ、409 の応答で段が読み直される。
- AC6（R17, R19）: フィードの契約の試験（`photo_feed_contract.rs` ほか）が、人の記録が無いときは変更なしで通る。
  契約の文書と `photo-feed.schema.json` の `quality_recommended` の説明文が更新され、Schema の差分が `description` だけ
  （`type`・`required` に差分が無い）。
- AC7（R20, R21, R23）: 結合試験で、`curation/confirm` は Content-Type や Origin が合わないと 403、`INGEST=0` で 503、
  64 KiB 超で既存の応答。`INGEST=0` かつ `photo_curation` 表の無い DB で `/api/v1/photos`・
  `/api/admin/curation/groups`・`/api/admin/library/*` が 200。新しい GET に POST・HEAD すると既存の決まりどおり
  （POST は 403）。
- AC8（R22, R24）: `tests/admin_api.rs` の完全一致の試験が通る。`cargo fmt --check`・clippy・`cargo test` が通る。
  `the_scripts_never_build_html_from_strings` が新しい JS にも通る。
- AC9（R9〜R11, R18。作ったときだけ）: 描画試験で年 → 月、都道府県 → 市区町村の階層が描かれ、押すと格子が出る。
  状況タブの件数が `GET /api/admin/curation/groups?state=unconfirmed&per=1` の `total` と一致する。

## 制約

- 技術: Rust（axum、rusqlite、`fast_image_resize`）＋素の JavaScript。静的ファイルは `build.rs` でバイナリに埋め込む。
  地図は同梱の MapLibre GL 4.7.1 と `/tiles/osm/`・`/tiles/gsi/` のプロキシ。新しい外部通信は作らない。
- 新しい環境変数は作らない（サムネイルの大きさ・上限は定数）。作るなら設定リファレンスと `EnvItem` と設定タブを
  同じ PR で直す。
- データベースの `SCHEMA` 定数は Python 版との一致の試験があるので、新しい表は AI の表と同じく別の定数で作る。
- PR は目的ごとに 3 本（下の実装の順番）。各 PR は単独でマージできる。戻す順番は実装の順番の節に書く。
- 本番機でビルド・試験はしてよいが、デプロイ・サービス操作・本番 DB への接続はしない。検証は合成データと
  `cargo test` で行う。
- 家庭 LAN の IP・ホスト名・鍵の内容・自宅の座標を文書・コード・PR・試験データに書かない。PR・文書に貼る画面写真は
  合成データだけにする（本番のコピーで目視した地図は貼らない）。
