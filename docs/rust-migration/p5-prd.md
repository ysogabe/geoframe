# P5（本番切替）PRD

- 要求の元: [Issue #54](https://github.com/ysogabe/geoframe/issues/54)、[plan.md P5](plan.md#p5-切替pr-6)
- 設計: [p5-design.md](p5-design.md)

## 背景と目的

P0〜P4で、Rust版`geoframe`（単一バイナリ）は検証環境で、本番と同じ写真を使った受入を通った。本番ではまだPython版（`geoframe-server`）が動いている。P5では本番をRust版に切り替え、そのあとPythonの実装と依存をリポジトリから外す。切替の前に、戻し方を演習で確かめておく。

## 使う人と場面

- **ユーザー（管理者）**: 本番の切替に立ち会い、切替の日時と、各段で先に進むかを決める。切替のあとは、管理画面・AI写真検索・旅行ブログを今までどおり使う。
- **miharashi**: 本番機の`http://127.0.0.1:8080`から写真フィードを読み続ける。
- **管理者（Claude）**: 手順書に従って演習と切替を行い、結果を記録する。

## ゴール / やらないこと

ゴール:
- 本番でRust版が、Python版と同じDATA_DIR・`catalog.db`を使い、取り込み・配信・管理・ローカルのAIを動かしている。
- 問題が出たら、手順書の手順でPython版へ戻せる。**戻しの猶予期間**（本番のPythonのvenvとunitを残しておく期間。§決まっていないこと）のあいだは、数分で戻せる。その戻し方を検証環境で演習している。
- 切替のあと、Pythonの実装・依存・CIのジョブ・Python版のunitがリポジトリから無い。Rust版のビルドとテストはPythonを実行しない。

やらないこと:
- クラウドのAI（Geminiの写真比較・撮影地の候補）を切替と同時に有効にすること。切替の数日後に、日の上限を小さくして有効にする（手順はP5で書く。実施はPRの外の運用作業）。
- PythonのAIを有効にしたまま戻すこと（戻すときはAIを無効にする。2026-10-29 ユーザー決定）。
- 初回のEmbeddingを本番のコピーで先に済ませること（切替のあと意味検索が約48分503になるのを受け入れる。2026-10-29 ユーザー決定）。
- 画面の作り直し、新機能。

## 要求

- R1（必須）: 本番でRustが書き込みを始められるようにする。検証環境の印の検査を外す。PythonとRustが同時に書かない守りは、バイナリの検査（Python版のunitが非稼働）・unitの`mask`・`Conflicts=`と順序・手順で持つ。AIの書き込み系の操作は、サービスと同じユーザー・設定で動かす道具を使う。
- R2（必須）: 本番へRustのバイナリを配る道具。本番であることを確かめ、演習で使ったのと同じバイナリだけを入れ、空のDBで「成功」としない。失敗したら前の状態へ戻す。
- R3（必須）: `catalog.db`と、バックアップに入っていない一次データ（旅行ブログの下書きなど）を切替の直前に保全する手順。バックアップから復元する手順と、その演習。
- R4（必須）: 切替の手順書。止める順・設定・確かめること・止める判断の基準・AIの書き込み系の操作の仕方。
- R5（必須）: Python版へ戻す手順（AIは無効を設定で強制）と、戻したあとRustへ切り替え直す手順。両方を、本番と同じunit名・同じDATA_DIRの配置で検証環境で演習する。
- R6（必須）: 本番のコピーを使った通しの演習（シャドー比較を含む）を、本番に入れるのと同じバイナリで済ませてから本番へ入れる。
- R7（必須）: ユーザーの立ち会いのもとでの本番の切替と、その記録。
- R8（必須）: 切替のあと、Pythonの実装と依存をリポジトリから外す。Rustのビルドが読む画面のファイル・旅程を移し、Pythonを実行するテストを外し、CIのPythonのジョブと文書を直す。本番のPythonのvenvとunitは、戻しの猶予期間が終わってからユーザーの許可を得て外す。
- R9（必須）: Rustの位置の手がかり（Decision）の待ちを、STATUSの`db.loc.clue_pending`が正しく表す。毎朝のDecisionのtimer（`loc_decision_morning.py`）が切替のあとも待ちを見落とさない。
- R10（あると良い）: 切替のあと数日の確認項目（Decisionの全件再判定の終わり、索引の公開、バックアップのtimer）と、クラウドAIを有効にする手順。

## 受け入れ条件

- AC1（R1）: `GEOFRAME_INGEST=1`のRustが、印の無い機体で、Python版のunitが無い・非稼働なら起動して書く。Python版が稼働中なら、`serve`と書き込み系のCLI（`sync`・`quality-scan`・`ai-jobs retry|release-pause|deactivate-space`など）は書く前に断る。検証環境の印の検査・`GEOFRAME_TEST_STAGING_MARKER`がバイナリの側に残っていない（`rust-deploy.sh`の印の扱いは除く）。検証環境の演習で、`Conflicts=`と順序により、どちらの向きでも旧プロセスが終わってから新しいプロセスが書き始めることを確かめた。
- AC2（R2）: `rust-deploy.sh --production=<ホスト名>`は、sshを使わずその機体で動き、ホスト名が違う・検証環境の印がある・Python版が稼働中・`geoframe-rs`がmaskされている・期待するsha256やcommitと違う・作業ツリーが汚れている、のどれかで何も変えずに断る。`--check-only`は変更の前の検査だけを行う。配布のあと配信の件数が指定の下限より少なければ失敗として戻す。`--rollback --production`が動く。`deploy-pull.sh`は、checkoutの固定の印があるとき、または`geoframe-rs`がenabled・active・maskedのとき断る。`rust-deploy-test.sh`と`deploy-pull.sh`の試験がこれらを試し、通る。演習で本番と同じ経路（`--production`）を通した。
- AC3（R3）: 検証環境で、手順書のとおりにバックアップから復元し、**起動する前に**`integrity_check`がokで`.dump`のSHA-256がバックアップと一致、ファイルの所有者がすべてサービスのユーザーであることを確かめた。起動のあと配信が200で、表示の画像の欠けが無い（あれば数と直し方を記録）。
- AC4（R4・R6）: 検証環境で、新しい本番のコピーと本番と同じ配置（Python版を`geoframe-server.service`・同じDATA_DIR・8080で置く）を使い、手順書のとおりにPython→Rustへ切り替えた。停止から配信の再開までの時間を測った（5分以内）。Pythonの配信にあった写真がRustの配信にすべてあり、増えた分は既知の差（[p4-acceptance.md §7.3](p4-acceptance.md)）で説明できる。シャドー比較（`tools/compare_with_python.py`）で想定外の差が0。取り込みの1サイクルとローカルのAIが動いた。結果を`p5-acceptance.md`に記録した。
- AC5（R5）: 検証環境で、Rust→Python（AIは設定で無効）へ戻し、DBを保ったまま配信・管理操作が動き、Rustの期間にした手動の位置・お気に入り・除外・回転・旅行ブログの下書きが保たれた。戻したPythonからAIの通信が出ていないことを確かめた。品質の切り戻し（[server.md §16.10](server.md#1610-rustで作った結果をpythonへ切り戻すp5のロールバック)）は、そのまま戻す場合と`dirty`の再構築が走った場合の件数・行数・グループ数を記録した。そこから再びRustへ切り替えて動いた。戻すのにかかった時間を記録した。
- AC6（R7）: 本番で、Pythonを止めたあとにバックアップと一次データの保全を取り、手順書のとおりに切り替えた。`/healthz`と`/api/v1/photos`が200で、AC4と同じ基準で写真がそろい、miharashiの表示が続き、取り込みのサイクルが成功した。停止から再開までの時間とともに`p5-acceptance.md`に記録した。
- AC7（R8）: リポジトリに`app/`のPython・`requirements*.txt`・`deploy/geoframe-server.service`・Python版の配布手順が無い。Rustの試験はPythonを実行しない（`crates`に`python`を起動するコードが無いことを試験かCIで確かめる）。CIのRustのジョブはPythonを導入しない。画面のファイル・旅程は新しい場所から埋め込まれ、埋め込みの表（パスと中身のハッシュ）が移す前と同じ。
- AC8（R9）: Rustの位置の手がかりのジョブに待ちがあるとき、STATUSの`db.loc.clue_pending`が0でない（試験）。旧Pythonの判定済みの行があるDBで、待ちが見え、Decisionが動けば進むことを演習で確かめた。
- AC9（R10）: 切替のあとの確認項目と、クラウドAIの有効化の手順（サービスを止め、サービスと同じユーザー・設定でCLIを動かし、起動し直す）が手順書にある。

## 制約

- 本番機（この開発機と同じ機体）では、ユーザーの立ち会いと各段での明示の許可なしに、サービスの停止・起動・配布・`/var/lib/geoframe`への書き込みをしない。切替の前は本番の`catalog.db`に直接つながない（読むのはバックアップのファイル）。切替のあとの確認で読むのは、サービスと同じユーザーでの読み取りだけ。
- 秘密情報（鍵・設定の値）・LANのアドレス・写真のファイル名・座標・地名は、リポジトリ・文書・PRに書かない。
- PythonとRustが同時に`catalog.db`へ書かない。
- 配信の停止は5分以内を目標にする。意味検索の503（約48分）と、Decisionの全件再判定で本番機のCPUを約4時間使うことは受け入れ済み。

## 決まっていないこと

- 本番の切替の日時（検証環境の演習のあとにユーザーと決める）。
- 戻しの猶予期間の長さ（設計の既定は、クラウドAIを有効にしてから1週間）。
- クラウドAIを有効にする日と日の上限（切替の数日後。ユーザーが決める）。
- 本番の設定に足す値（AI設定のJSONの中身・`GEOFRAME_TILE_UA`など）。値は切替の準備でユーザーと確かめる。
