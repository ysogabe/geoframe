- 実行先は検証用LXCのみ。本番のサービス・設定・DB・画像は変更していない。検証用の元DBも変更せず、書く試験はすべて専用の複製で行った。Drive側のファイルは追加・変更・削除していない（`drive.readonly`）。
- 地名検索の変更は`0acfc2c`。musl静的バイナリ（17,297,136 B、SHA-256先頭`cc0583c2c63fc950`）を`rust-deploy.sh`で検証環境へ配布し、ヘルス確認成功。Driveの46枚比較と保留の初回表示は配布前のP3バイナリ、それ以降の新規索引・保留解除・HEIC原本検査・地名検索は`0acfc2c`。Drive・画像処理・保留表示の実装はこの変更で変わらない。

## 1. 本物のDriveでの冪等性

本番コピーの複製に対する`sync --dry-run`と、取り込み有効の実サイクルの両方で:

- `index_drive`: `remote=6535 pages=7 unchanged=6535`、`added=0 updated=0 removed=0`、削除の保留0。
- `fetch_derivatives`: `pending=0`。dry-runの`planned=0`、実行の取得0。
- 表示可能5,288 / 取得待ち0 / 全6,535。dry-run・実サイクルとも終了コード0。
- 複製DBの`.dump`のSHA-256が、実サイクルの前後で完全一致。

**合格。既存の索引と画像を変更・再取得しない。**

## 2. 同じDrive原本のRust/Python比較

形式ごとに最大20枚を選んだ（JPEGは`.jpg`と`.jpeg`を別々に選定）。同じバックアップの複製2つを作り、選んだ行の`display`をNULLに戻した。既存画像はハードリンクで複製し、選んだ画像のリンクは複製側だけ先に削除して、元の実体への上書きを避けた。

Rustの実同期と比較用Pythonの`fetch_derivatives`で、同じDrive IDの原本をそれぞれ取得・変換した。Rustの索引は更新0で、比較後の再索引でも更新0（原本のMD5に変更なし）。Pythonのログは非公開の試験領域で保持し、結果だけを集計した。

| 形式 | 標本 | Rust成功 | Python成功 | 出力寸法の不一致 |
| --- | ---: | ---: | ---: | ---: |
| JPEG（`.jpg`） | 20 | 20 | 20 | 0 |
| JPEG（`.jpeg`） | 1 | 1 | 1 | 0 |
| HEIC | 20 | 20 | 20 | 0 |
| PNG | 5 | 5 | 5 | 0 |
| 合計 | 46 | 46 | 46 | 0 |

- Rustだけが失敗する写真0。`icc_dropped=0 original_remove_failed=0`。ダウンロード用の`tmp/.dl_*`の残り0。
- 変換後の再同期の計画は追加・更新・削除・取得予定がすべて0。
- 対象フォルダにTIFF・HEIFの標本は無かった。この結果は46枚の標本の範囲であり、全形式・全撮影モードの保証ではない。

**受入条件①に合格。** 受入条件②（恒久失敗の後続取得）・③（一時ファイルの作り方）は従来のスタブ試験の確認を維持。

## 3. 実機iPhoneのHEIC原本

HEIC標本の中から5枚を検証環境内だけへ再取得。5枚ともDBの原本MD5と一致し、EXIFの機種がiPhoneであることを値を出さず件数で確認した。

- 5/5枚が`img-probe`成功、失敗0。
- 入力4,032×3,024、出力2,560×1,920、ICCはsRGB。
- Pillow HEIFの報告は5枚とも8ビット。先頭のメタデータ領域に`grid`タグが5枚とも存在（この検査は構造の完全な解析ではない）。
- 10ビット・HDR・Live Photoなどの個別のモードはこの標本では確認していない。HEIC全体の互換性は§2の20枚とこの5枚の実測の範囲。

## 4. 実Driveの未登録写真を索引から配信まで通す（S2）

Drive側への合成JPEGのアップロードに代え、実DriveにあるGPSつきJPEG1枚を複製DBから外し、未取り込みの状態を作った。複製側の画像も削除。実際のDrive一覧・原本・メタデータを使い、未登録行を発見して配信する経路を確かめた。Drive側での追加・削除操作は行っていない。

1. dry-run: `added=1 pending=1 planned=1`。
2. 実同期: `added=1 fetched=1 ok_jpeg=1`、終了コード0。
3. 新しい行は`source='drive' loc_source='drive_meta'`、緯度あり、derivativeあり。
4. この複製を読み取り専用で配信し、画像はHTTP 200・JPEG。フィードは3,065件（元と同じ件数まで回復）。
5. 再同期の計画は追加・更新・削除・取得予定すべて0。

**S2の索引→取得→位置→配信→再同期は合格。新しいファイルをDriveへアップロードした直後の見え方は、この方法では試していない。**

## 5. 大量削除の保留とSTATUSタブ

専用の複製に、Driveに存在しない試験用の行を2,000件追加。元の6,535行と合わせて8,535行にした。実際のDrive一覧6,535件と比較する取り込み有効の専用`serve`を起動した（原本取得は0枚に設定）。

- `sync.mass_delete_hold`: `held=2000 reason='ratio' drive_rows=8535`。試験用の行は消えず、全8,535行を保持。
- ブラウザでSTATUSタブを開き、描画画像と本文を確認。「Driveの削除を保留中」「2000件」、50件超かつ20%超の理由、開始・最終確認の時刻、`geoframe sync --allow-mass-delete`、画面から解除できない旨が表示された。
- 専用サービスを止め、**複製にだけ**`sync --allow-mass-delete`を実行。`removed=2000`、保留0、画像の削除0、全6,535行へ戻り終了コード0。
- 専用サービスを再開し、実Driveへの同期完了後にAPIの`mass_delete_hold`が無いことと、ブラウザから保留の注意が消えたことを確認。元の写真は削除されていない。

**表示と解除の両方に合格。**

## 6. NominatimのUser-Agentと実通信

ユーザーが既存の連絡先入り`GEOFRAME_TILE_UA`を共用すると決定。`0acfc2c`で`Config.tile_ua`を地名検索へ渡し、地理院・Nominatim双方へ同じ値を送るようにした。設定値はDebug・起動ログに出さない。

- 配布後のサービス環境に連絡先入りUAがあることだけを確認（値は記録しない）。通常のサービスは取り込み無効のまま。
- 公開ランドマークの地名検索で地理院が0件となり、Nominatim由来の結果が2件、HTTP 200。1回目1.055秒。
- 同じ要求を繰り返すと0.017秒で同じ2件。結果全体が一致し、Nominatimのメモリキャッシュを利用。
- 毎秒1件の待機・排他は既存試験で確認。設定したUAが両方のスタブへ届くこと、未設定・空文字の既定、失敗ログにUAを出さないことも追加試験で確認。
- `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`成功（739件）。通常レビュー（Sol）で必須・推奨・参考すべて0。
- 利用条件: [Nominatim Usage Policy](https://operations.osmfoundation.org/policies/nominatim/)（識別可能なUA、最大毎秒1件、結果のキャッシュ。手動の地名検索のフォールバックとして使用）。
