# 3D PHOTO JOURNEY: 地形の奥行きとサイバー表示の検討

ステータス: 奥行き改善は実装済み・実機未反映、サイバー表示は検討段階（2026-09-08）  
対象: N100 の 2560x1080 実機表示  
方針: この文書だけでは通常表示を切り替えない。衛星写真を残す選択肢と、衛星写真を使わないサイバー表示の試作を比較する。

## 実機スクリーンショットから確認できること

実機の 2560x1080 スクリーンショットでは、広い背景の航空・衛星写真が全体に柔らかく、地表の用途や細部を読み取りにくい。背景は平野に見え、地形の起伏はほとんど知覚できない。建物の立体形状も表示されていない。HUD の暗いパネルとシアン、緑、マゼンタのアクセントは既にサイバー調として成立しているが、中央から右側に浮く複数の写真カードと大きな写真パネルが地形の読み取りと視線を競合させている。

これは表示結果の所見であり、写真の個別内容、座標、ホスト名、取得元の個人パスはこのロードマップに記録しない。

## コードから確認できる原因

スクリーンショットの所見と、実装上確認できる要因を分けて整理する。

今回の検証では、実機から取得した画面画像を現状確認に使い、表示案の比較は
サーバーの実タイルを読み込む別のローカルブラウザで行った。後者の描画時間や
メモリ値はN100実機の性能測定ではない。

富士山を注視する同じカメラで、約25秒時点では粗い平面が残り、更新を続けた
約70秒時点では山頂・斜面が立ち上がった。標高の点サンプルが約3,700mを返していても、
可視範囲の地形メッシュや画像が完成しているとは限らない。通常の描画精細化を
12秒で止める設定では待ち時間に余裕がなかった。ただし、比較には継続描画の有無も
含まれるため、12秒の期限だけを原因と断定できない。航空機イベントによるカメラ
移動も確認しており、比較時はその割り込みを分けて検証する。

| 要因 | コード上の根拠 | 表示への影響 |
| --- | --- | --- |
| 内部レンダー解像度が半分 | `frontend/photo-journey-lite.js` の通常設定は `pixelRatio: 0.5`。CSS 2560x1080 でもレンダーターゲットは概ね 1280x540 になる | 写真の細部、細い線、地形の陰影が最初から半分の画素密度になる。画素数は縦横それぞれに効くため、GPU 負荷を下げる一方で見た目の余裕が少ない |
| 衛星写真のズーム帯が混在 | `app/geoframe/config.py` の `GSI_PHOTO_TILE_BANDS` は z2–13 が Landsat8、z14–18 が seamless photo。各タイルは `app/geoframe/tiles.py` で 256x256 の PNG/JPEG を検証し、意図的な拡大縮小はしていない | 広域表示で z2–13 の粗い画像が見える範囲が広い。z14 以上を待てない範囲や取得できない範囲は、細部のない画像として見える |
| LOD と低電力設定 | 通常設定は `segments: 32`, `maxSse: 4`。`?low` の `LOW_POWER_OPTIONS` は `segments: 16`, `maxSse: 8`、LOD fog/dynamic SSE と SSE multiplier の上限も強い | `low` では粗い地形メッシュと遠方の粗いタイルを許容する。端末起動 URL に `low` が付いていないかを実機で確認する必要がある |
| 取得待ちとキャッシュの圧力 | 写真の通常 prefetch は国内 z15/z16、低電力時は z14。通常キャッシュは 512 MiB だが、過去の航空写真のみの測定でも 131 タイルで GPU 推定約 440 MiB | DEM、hillshade、写真、写真カードを同時に保持すると、全範囲を高ズームで揃える余裕が小さい。取得待ちや予算調整中は祖先タイルが長く残る可能性がある |
| 画像取得の失敗時の挙動 | `app/geoframe/tiles.py` は通常ラスタの取得失敗時に透明 PNG を返す。Navara 側の LOD が祖先タイルを選ぶこともある | 通信の遅延・スロットリング・欠損は、ぼけまたは穴として現れ得る。これは単なる色調の問題ではない |
| DEM の表現範囲 | DEM は `app/geoframe/config.py` で z0–8 が全球の粗い範囲、z9–14 が国内中心。`frontend/photo-journey-lite.js` は DEM terrain と hillshade を追加する | DEM は標高の面を作るだけで建物を作らない。低起伏の平野は正しくても平らに見え、建物の立体感には別の建物・ベクターデータが必要 |

したがって、写真の粗さは `pixelRatio`、写真ソースのズーム帯、LOD/取得予算が重なった結果であり、DEM の採用だけで写真の解像度や平野の起伏を補えるわけではない。現在のコードは `terrain` を `hillshade` より先に置き、写真ラスタをその上に重ねる構成なので、衛星写真を外す場合はラスタの追加と prefetch 自体をスタイルに応じて抑える設計が必要になる。

## 今回実装した奥行き改善

- 撮影地点をカメラ位置として扱わず、後方からその地点を見込む配置へ変更。
- 通常は地面から1,400m、俯角24度。既知の実標高を優先し、実標高がない写真はDEMで再評価。
- 夜側で斜光が消えないよう、地形照明用の太陽日時を地点の地方太陽時15時に固定。
  これは鑑賞用照明であり、現在の実際の日照を示すものではない。
- 通常・省電力とも90秒以上滞在し、描画精細化をそれぞれ55秒・60秒に延長。
  更新間隔は400ms・800msで、常時アニメーションは無効のまま。
- 通常時は到着45秒後から8秒間、22度だけ撮影地点を周回。省電力・動きを減らす
  設定では周回せず、航空機アラート・スリープ・ページ終了では停止。
- 次の地点のDEM親タイルも既存の取得レート上限内で先読み。画面に固定された
  格子を隠し、走査線と周辺の暗転を弱めて、地形の輪郭を見やすくする。

カメラは撮影地点を基準に配置するもので、未取得の周辺地形との衝突回避を保証する
ものではない。また、この改善で衛星画像の元解像度や建物データが増えるわけではない。

サーバーの実タイル・写真を使い、航空機割り込みを除いたローカル比較では、35秒時点に
粗い面が残り、55秒時点に稜線と山の重なりを確認した。初期読み込みの待ち時間と
画像のぼけは残るため、精細化後の鑑賞時間を確保できる90秒滞在とした。
DEMの開始ズームを8へ上げる比較も行ったが、同じローカル環境の35秒時点で
GPU推定値が約141MiBから477MiBへ増加し、大量のタイル破棄が発生したため採用しなかった。

以下はこれと別に検討する表示スタイルの選択肢であり、通常表示にはまだ追加しない。

## 表示案の比較

### A. 衛星写真を残す

写真は土地利用や市街地の意味をすぐ伝えられ、別の等高線生成も不要である。既存の `gsi-photo` 経路、帰属表示、写真表示との関係を保ちやすい。一方、現在のスクリーンショットに出ているぼけの原因をそのまま抱え、広域では z2–13 の粗い写真、半分のレンダー解像度、タイル予算の競合が残る。写真を残すなら、通常表示の候補として明示し、z14 以上が揃うまでの待ち時間、実際の最高ズーム、GPU 使用量を測ってから品質設定を決めるべきである。

### B. 衛星写真なしの塗りつぶし地形

DEM terrain を暗い青で塗り、hillshade または標高のカラーマップを弱く重ねる。`view.globe.color`、`view.globe.elevationColormap`、`elevationHeatmap` は Navara の公開型にあり、写真ラスタを外せば画像タイルの GPU/通信予算を使わずに済む。現在の HUD とも合わせやすい候補である。ただしローカル試作では65秒後も灰色の面が主体で、標高色による明瞭な地形表現はまだ成立していない。API の存在と完成した表示品質は別であり、採用前に色と陰影の描画経路を検証する。

弱点は、平野の低い起伏が平らに見えること、建物を生成しないこと、強い標高カラーマップを使うと地理的な説明より抽象表現が先に立つことである。これは「立体地形」の改善案であり、建物表示の解決案ではない。

### C. ワイヤーフレーム

Navara の公開 API `view.globe.wireframe = true` を使い、DEM のタイルメッシュを線で表示する。追加の等高線計算や新しいデータサービスが不要で、サイバー調の技術試作として最短で評価できる。地形の三角形メッシュが見えるため、カメラ周回や照明の効果も確認しやすい。

ただしこれは等高線ではなく三角形のメッシュ線である。`segments` と LOD により線密度が変わり、遠景では線が粗くなったりエイリアシングしたりする。また `wireframe` は地球儀の地形メッシュ全体に効くため、「塗りつぶし地形の上に必要な場所だけ線を置く」最終表現をそのまま実現する API ではない。実際の試作では線が過密になり、手前の面を透かして奥側の線も見えるため雑然とした。全面ワイヤーを常用表示に採用するのは避け、地形確認用に限定する。

| 案 | 視認性 | 資源と実装 | リスク | 用途 |
| --- | --- | --- | --- | --- |
| 衛星写真あり | 土地利用は分かりやすいが、現状のぼけが残る | 既存経路を利用できるが写真タイルの通信/GPU 費用が高い | 低ズーム、取得待ち、品質の場所差 | 明示的な写真モード |
| 衛星写真なし・塗りつぶし | 暗い面と輪郭を見せる設計候補。試作はまだ灰色面主体 | DEM と標高色の描画経路を要検証 | 平野は平ら、建物なし | 次に検証するサイバー地形の候補 |
| ワイヤーフレーム | 山の形は確認できるが、線の過密と透けが目立つ | 公開 API 一つで試作できる | 等高線ではない、線密度が LOD 依存 | 地形確認用 |

## 推奨方針

目標の表示は、衛星写真を主役から外した暗青色の塗りつぶし DEM terrain に、現在地点や短い経路の周辺だけシアンの線を重ねる構成とする。これが「写真が粗い」問題を写真の高解像度化だけに依存せず、既存 HUD のサイバー調とも合わせられる。写真地図は `photo` と `cyber` の明示的なスタイル切替として残せるが、ユーザーの検討依頼だけを理由に通常機能をサイバーへ勝手に切り替えない。

全面ワイヤーの試作結果を踏まえ、次は塗りつぶし面の色・陰影を成立させ、小範囲のシアン線を重ねる。これは未実装の提案であり、今回のカメラ・照明・周回の修正とは区別する。建物や等高線の全面生成は初期範囲に含めない。

Navara の公開型には GeoJSON source と `PolylineMaterial` の `clampToGround` があるため、局所線は小さな GeoJSON polyline として追加できる。ただし公開型に DEM から等高線を作る機能は見当たらない。等高線を採用する場合は、表示中の DEM ピクセルを粗い格子に落として marching squares 等で線を作り、対象範囲と本数を制限する小さな自前処理が必要になる。新しい外部サービスや依存を導入せず、MVP 後の段階とする。

## 段階実装

1. `terrainStyle=photo|cyber` のような明示的な設定境界を設ける。`photo` は既存の通常表示を保ち、`cyber` は `gsi-photo` の追加と写真 prefetch を行わない。帰属表示とスタイルの初期値を確認する。
2. `cyber` の技術試作として DEM terrain の塗りつぶし色と陰影の描画経路を確認する。全面 wireframe は確認用にとどめる。等高線、建物データ、追加のネットワークサービスはこの段階に入れない。
3. 推奨形へ進める場合は、暗青色の地形塗りを基礎に、弱い hillshade または `ColorMap` による標高差を加える。現在地点・周回経路の小範囲だけに、`clampToGround` のシアン polyline を置く。線幅、頂点数、透明度は N100 の実測で決める。
4. 写真切替を追加する。切替時のラスタの破棄・追加、帰属、タイル取得待ちを確認し、デフォルトが変わっていないことを回帰確認する。
5. 平野でも地形を読ませる必要が残る場合だけ、限定的な等高線を検討する。建物の立体感が要件になった場合は、DEM と別の建物データ・表示レイヤーが必要であり、このロードマップの MVP の範囲外である。

## 測定と QA

- 同じ 2560x1080 実機条件で、現行スクリーンショットと各スタイルを比較する。写真の細部、地形の輪郭、HUD と写真カードの競合、線のちらつきを同じ距離・周回で記録する。
- Navara の `view.memoryStats()` から `gpuBytesEst`、`fixedGpuBytes`、`budgetBytes`、`sseMultiplier`、保持中の terrain/raster タイル数を取得し、写真あり・cyber・wireframe で比較する。過去の航空写真のみの約 440 MiB はコード上の推定であり、DEM と hillshade を加えた現在値ではない。
- scrot は初期表示・タイル安定後・周回中の静止画取得に使う。FPS、p95 フレーム時間、長フレーム数は、独立したテストブラウザの描画計測で別途取得する。短時間の見栄えだけでなく 10–30 分の連続表示、メモリ増加、周回の完了、復帰を確認する。
- 平野、起伏のある地域、海岸・海外など DEM の欠損可能性が異なる場所を使う。欠損時に透明面や不自然な色が広がらないことを確認する。
- 「地面だけで建物が立体になる」という判定は行わない。建物を必要とする場合は別レイヤーの設計・データ量・帰属・予算を別途測る。
