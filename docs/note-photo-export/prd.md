# note 記事用の写真書き出し PRD

- 状態: 計画（設計のみ。実装は未着手）。判断 U1〜U7 は 2026-11-22 に決定済み、U8 は判断待ち
- 開始: 2026-11-20
- 設計: [design.md](design.md)

## 背景と目的

note の山行記・旅行記を書くとき、対象日の写真を GEOFRAME のカタログから集め、Google Drive 経由で受け取っている。今は記事のたびに T3 のスレッドを立て、次の手順を手で回している。

1. 写真フィード `GET /api/v1/photos` を全件取り、撮影時刻（`time`、ローカル時刻＝日本時間）の日付で絞る。
2. 該当写真の表示用 JPEG（`derivatives/<名前>.jpg`）を取る。原本（フル解像度）はこの経路では取れない。
3. 1 枚ごとの情報を `manifest.json` にまとめる。
4. rclone で写真と manifest を Drive の `gdrive:yamareco/<日付>/`（旅行記は `gdrive:travel-journal/<日付>/`）へコピーする。
5. 受け取り側（別 VM のエージェント）は Drive から取り、manifest と実ファイルのサイズを突き合わせて検証する。

この手順を GEOFRAME の機能にして、呼び出し側のエージェントが tailnet 経由で直接呼べるようにする。手作業の T3 スレッドを不要にし、毎回同じ形の manifest が出るようにする。

この機能は、今は無効にしている旅行ブログの機能（`GEOFRAME_BLOG`）で作りたかったものである。書き出し機能が完成したら、旅行ブログの機能は削除する（2026-11-22 のユーザーの指示。削除は別の作業で行い、この PRD の範囲に含めない）。

## 使う人と場面

- **呼び出し側**: 別 VM のエージェント。記事を書く日付が決まった時点で、日付（または期間）と書き出し先の種類を指定して呼ぶ。
- **人**: 本人（オーナー）。呼び出しが失敗したときや、再実行の可否を判断するときに結果を見る。

## ゴール / やらないこと

### ゴール

- 日付または期間と、書き出し先の種類（山行 / 旅行記）を指定すると、その期間の写真と manifest を Drive へ書き出せる。
- 対象は、その期間に撮った**全写真**（非表示を除く）とする。重複・類似で非推奨になった写真も含める（2026-11-22 の判断 U1）。
- 結果（枚数、書き出し先、manifest の中身の要約）を機械で読める形で返す。写真が 0 枚のときも、0 枚だと明確に返す。
- 受け取り側の今の検証（manifest と実ファイルのサイズの突き合わせ）が、そのまま通る manifest を出す。

### やらないこと

- 原本（フル解像度）の書き出し。表示用 JPEG（長辺 2560px）だけにする。表示用 JPEG の作り直しもしない（今あるものをそのまま送る）。
- 撮影時刻の補正。一眼（DSC）写真の時刻が日本時間のままの日があっても、書き出し側では直さない。カタログの値をそのまま出す。
- 名所（`spot`）の付与。今の環境に名所の一覧が見つからないため、空欄にする。山行の旧 manifest も空欄だったが、旅行記の旧 manifest には名所の名前と距離が入っていたものがあり、旅行記ではこの分が欠ける（設計 U8。判断待ち）。
- note への投稿、記事本文の生成。
- 写真サービス（`geoframe serve`）の既存の動作の変更。写真サービスには、読み取り専用の API を 1 つ足すだけにする（設計 3.1 の A′）。
- Drive の権限と共有範囲の変更。今の書き出し先（`yamareco/`・`travel-journal/`）の権限と共有設定をそのまま使う（判断 U4・U7）。

## 要求

- **R1（必須）**: 日付 1 日、または開始日と終了日（両端を含む）を指定して書き出せる。日付はカタログの撮影時刻（ローカル時刻）の日付部分で判定する。
- **R2（必須）**: 書き出し先を種類（`yamareco` / `travel-journal`）で指定する。Drive 上の実際のパスはサーバー側で決め、呼び出し側から任意のパスを渡せないようにする。
- **R3（必須）**: 対象の写真は、期間内に撮った全写真のうち非表示でないものとする。位置の無い写真、重複・類似で非推奨の写真も含める。撮影時刻が空・形が崩れた写真は、日付が分からないので対象にしない。表示用の派生画像でないもの（EXIF 付きの原本）は外へ出さない。対象外にした件数と理由は結果で知らせる。表示用 JPEG がまだ作られていない写真（取り込みの直後など）が期間内にあれば、一部が欠けた書き出しを作らず、失敗にして知らせる（R5b）。
- **R4（必須）**: manifest.json は、旧 manifest（2026-11 時点の手作業の形式）と互換にする。1 枚ごとに、ファイル名（`HHMMSS_<id>.jpg`）、`id`、`title`、`taken_at`、`lat`/`lon`、`elev`、`gps_inferred`、`width`/`height`、`file_size`、`mean_brightness`、`sharpness_laplacian_var`、`spot`、`nearest_spot_distance_m` を入れる。`gps_inferred` は必ず入れる。位置の無い写真では `lat`/`lon` を `null` にする（旧 manifest には無かった値）。
- **R5（必須）**: 対象の日の写真が 0 枚なら、正常な結果として返す。エラーにしない。Drive には何も書かず、フォルダも作らない（判断 U5）。
- **R5b（必須）**: 書き出しの対象にした写真が 1 枚でも取れない・読めないときは、一部が欠けた書き出しを Drive に公開しない（ジョブを失敗にする）。
- **R6（必須）**: 同じ書き出し先（種類と日付）に既にフォルダがあるときは、既定では書き出さずに知らせる（上書きしない）。明示したときだけ置き換える（API からも許す。判断 U6）。置き換えられるのは、このサービスが前に書き出し、その後に中身が変わっていないフォルダだけにする（手作業で作ったフォルダや、後からファイルを足したフォルダは置き換えない）。置き換えでも、宛先に見えるのは検証済みの一式か前の一式のどちらかで、前の一式は Drive のゴミ箱から戻せる（ゴミ箱は 30 日で自動的に空になる）。ただし置き換えの数秒のあいだは、宛先が一時的に無くなることを許す（受け取り側は、無ければ少し待って取り直す）。途中で止まって状態を照合できないときは、次の書き出しを止めてオーナーに知らせる。
- **R7（必須）**: 呼び出し側のエージェントから tailnet 経由で直接呼べる。認証（トークン）と、送信元の制限を掛ける。
- **R8（必須）**: 書き出しは 1 度に 1 件だけ動かす（HTTP からもコマンドからも）。実行中に次の要求が来たら断る。
- **R9（必須）**: 呼び出し側は、書き出しの受付と完了を別々に確かめられる（受付で ID を返し、ID で状態と結果を引ける）。受付の応答を受け取れなかったときやサービスの再起動の後でも、同じジョブを引ける。
- **R10（あると良い）**: 実際には書かずに、対象の枚数と書き出し先だけを返す確認（dry run）ができる。
- **R11（あると良い）**: 同じ機能を、ホスト上のコマンドからも実行できる（T3 からの手作業の代わり、障害時の手動実行）。

## 受け入れ条件

- **AC1（R1）**: 写真がある日 D を指定すると、撮影時刻の日付が D である写真のうち、R3 で対象外にするもの以外がすべて、かつそれだけが書き出される（偽の写真サービスを使う試験で確かめる）。期間 D1〜D2 を指定すると、両端の日を含む。開始日が終了日より後、日付の形式が不正、期間が上限を超える指定は 400 で断る。
- **AC2（R2）**: `destination` が `yamareco` / `travel-journal` 以外なら 400 で断る。rclone に渡す宛先は、種類ごとの固定の接頭辞と、検査済みの日付から作った名前だけになっている（試験で rclone の引数を記録して確かめる）。
- **AC3（R3）**: 非表示の写真、撮影時刻が空・形が崩れた写真、派生画像でない写真は書き出されない。重複・類似で非推奨の写真と、位置の無い写真は書き出される。結果に、対象外にした件数と理由が出る。表示用 JPEG がまだ無い写真が期間内にあれば、状態は失敗（`derivative_pending`）で、Drive は変わらない。
- **AC4（R4）**: 書き出した manifest が、旧 manifest のキーをすべて持つ。`file_size` が Drive 上の実ファイルのサイズと一致する（受け取り側の今の検証が通る）。`gps_inferred` がカタログの位置の由来（`inferred`）と一致する。位置の無い写真では `lat`/`lon` が `null`、`gps_inferred` が `false`。
- **AC5（R5）**: 写真が 0 枚の日を指定すると、状態は成功で `count: 0`、Drive への書き込みは行われず、フォルダも作られない（rclone を呼ばない）。宛先に既にフォルダがある日でも同じ。
- **AC5b（R5b）**: 対象の写真のうち 1 枚の取得かデコードに失敗すると、状態は失敗になり、Drive の宛先は変わらない。
- **AC6（R6）**: 既にフォルダがある宛先（空のフォルダを含む）に既定のまま書き出すと、状態 `conflict` で終わり、Drive は変わらない。`on_exists: "replace"` を付けると、このサービスが書いたフォルダなら新しい写真と manifest に置き換わり、前のフォルダは Drive のゴミ箱に移る。このサービスが書いたと確かめられないフォルダ（手作業のもの）は置き換えず、`conflict`（`not_managed`）で終わる。このサービスが書いたフォルダでも、前の manifest に無いファイルが足されていれば `conflict`（`modified`）で終わる。置き換えの途中で失敗・停止しても、宛先は前の一式か新しい一式のどちらかになる（復旧の表のとおり。照合できなければ次の書き出しを止める）。同じ名前のフォルダが複数ある、Drive に照会できないときは失敗にする。
- **AC7（R7）**: トークンが無い・違う要求は 401、許可していない送信元からの接続は 403 で断る。許可した送信元から正しいトークンで送れば受け付ける。トークンの値はログにも応答にも出ない。
- **AC8（R8）**: 書き出しの実行中に 2 件目を受け付けようとすると 409 で断る。コマンドから実行中のときも同じ。
- **AC9（R9）**: 受付で `202` とジョブ ID が返り、ID で `running` → `succeeded` / `failed` / `conflict` の状態と結果が引ける（最初の照会で完了が返ってもよい）。同じ要求 ID の再送には、実行中でも同じジョブが返る（直近 50 件）。再起動の後もジョブ ID で結果を引ける。
- **AC10（R10）**: `dry_run: true` では、対象の枚数・書き出し先の名前・既存フォルダの有無を返し、Drive に何も書かない。
- **AC11（R11）**: ホスト上のコマンドで、同じ指定・同じ結果の書き出しができる。成功・conflict・失敗が、決まった JSON と終了コードで分かる。

## 制約

- 写真のデータ（`/var/lib/geoframe`）は `geoframe` ユーザーの 0750 で、他のユーザーからは直接読めない。写真の一覧と表示用 JPEG は HTTP（`:8080`）から取る。
- Drive へのコピーは、オーナーのアカウントで認可した rclone を使う。設定はこの機能の専用のもの（専用の client_id で認可し直したもの）にし、オーナーのホームの設定は使わない。権限は今と同じ Drive 全体のままにする（判断 U4）。GEOFRAME の Drive の鍵（サービスアカウント、読み取り用）は使わない。
- 写真サービス（`geoframe-rs`）は無認証で、プロセスの外を呼ばない強いハードニングで動いている。この性質を崩さない（足すのは読み取り専用の API だけで、unit は変えない）。
- リポジトリは公開なので、tailnet の IP、トークンの値や置き場所の実パス、実際の撮影日は文書に書かない（配置時の設定に置く）。

| 番号 | 決定（2026-11-22） |
|---|---|
| U1 | その日の全写真（非表示を除く）。負荷を見積もり、重くないと確かめた（設計 2.9） |

| U7 | 書き出し先の今の共有設定をそのまま使い、共有を広げない |
