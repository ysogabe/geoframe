# 管理画面の整え直し（A） PRD

作成日: 2026-10-30。状態: レビュー 2 回を反映済み。ユーザー承認待ち。

## 背景と目的

管理画面は旧 Python 版から流用した 3 ページ（`/admin`・`/ai-search`・`/blog-admin`）で、
Rust 移行（Issue #54）では「作り直さず流用」が方針だった。2026-10-25 の目視で
「微調整は要るが最初の移行としては OK」と評価され、2026-10-30 に次の 4 点が問題として挙がった。

1. 「位置なし」「全写真」の 2 つのタブが分かりにくい。実体は同じ一覧でフィルタの初期値が違うだけで、
   同じカードが 2 つのタブに出ている（タブ名とカードの両方の問題）。
2. 旅行ブログ（`/blog-admin`）は作り直す予定なので、いったん無効にしたい。
3. 全写真の一覧と AI 写真検索は同じ場所にあるべき。
4. アプリの設定を見る場所がない。

本 PRD はこの 4 点を解く「A: 整え直し」の範囲を定める。写真ライブラリ（ADR 0008 の「後続で作る」画面、
G3）と選別の確認（G4）、運用コンソール（sync・quality-scan・AI ジョブの操作）は範囲外で、別の PRD にする。

## 使う人と場面

- 作者 1 人が、家庭 LAN 内のブラウザから使う。認証は無い（[ADR 0008](../decisions/0008-photo-platform-and-miharashi-display.md)
  の方針どおり、外部公開時は Cloudflare Access で認証する）。
- 場面: (a) 取り込み・AI の進み具合と異常の確認 (b) 位置なし写真への位置付け、お気に入り・除外・回転の操作
  (c) 言葉で写真を探して (b) と同じ操作をする (d) 今どの設定で動いているかの確認（特にクラウド AI の日の上限）。

## ゴール / やらないこと

ゴール:

- 1 枚の管理画面に「状況 / 写真 / 設定」の 3 タブを置き、今の 3 ページの機能（旅行ブログを除く）を失わずに収める。
- 旅行ブログを設定で無効にできる（既定は無効）。コードとデータは残す。
- 「写真」タブで、一覧の絞り込みと AI 検索を同じ画面で行える。カードは 1 種類。
- 「設定」タブで、起動時に読み込んだ設定を出どころつきで読める。秘密は出さない。

やらないこと:

- 設定の書き換え（画面からの変更）。読み取り専用に限る。
- 写真ライブラリ（日付・旅・地図で眺める画面）、サムネイル用の派生画像、選別の承認。
- 運用操作（同期・品質解析・AI ジョブの再試行・保留の解除）を画面から行うこと。大量削除の保留は
  件数と解除コマンドの表示のまま（2026-10-25 の決定）。
- 旅行ブログの作り直し。無効のあいだの API は 404 でよい。
- フレームワークやビルド工程の導入。素の JavaScript（classic script、依存なし）をバイナリに埋め込む方式を続ける。
- 表示（スライドショー等）の機能。表示は miharashi の責務。
- 本番への反映。マージまでが範囲で、本番の更新（ビルド → `/opt/geoframe` の更新 → `rust-deploy.sh --production`）は
  ユーザーの立ち会いで別途行う（P5 の猶予期間は 2026-10-30 21:20 に終わった）。
## 要求

### 画面の構成

- R1（必須）: `/` と `/admin` は 1 枚の管理画面を返し、ヘッダに「状況 / 写真 / 設定」の 3 タブを持つ（完成形。
  設定タブは PR ③ で足す。それまでは「状況 / 写真」の 2 タブ）。旅行ブログはナビに出さない。
- R2（必須）: `/ai-search` は「写真」タブ（PR ② から。それまでは今の AI 検索ページ）、`/blog-admin` は
  旅行ブログが無効のとき管理画面に導く。古いブックマークが 404 にならない。
- R3（必須）: admin.html・admin.js・ai-search.html の Python 時代の記述（`server.py`・`handlers.py`・`loc_suggest.py` への
  言及、「表示画面」リンク）を取り除く。

### 状況タブ

- R4（必須）: 今の STATUS（同期・DB 内訳・AI の待ち・ディスク・Drive の大量削除の保留）を失わない。
- R5（あると良い）: 「要対応」の件数（位置なし・AI 候補あり）を出し、押すと「写真」タブの該当フィルタへ移る。

### 写真タブ

- R6（必須）: 一覧のフィルタは 1 列のチップ 7 種（すべて・位置なし・AI 候補あり・推定・手動・★お気に入り・除外）で、
  各チップに件数を出す。タブは分けない。
- R7（必須）: 検索欄を置く。検索語を入れて検索すると、AI 検索の結果を場面ごとに出す（成功したときだけ一覧から
  切り替える）。「AI おすすめ」ボタン（検索語なしの推奨）も同じ場所に置く。検索結果を閉じると、直前のフィルタと
  ページの一覧に戻る。
- R8（必須）: AI 検索が使えないとき（AI 無効・索引が未公開・レート制限・検索語の誤り）は、検索欄の下に理由を
  日本語で出し、一覧はそのまま使える。
- R9（必須）: カードは一覧と検索結果で同じ 1 種類。★お気に入り・除外・位置の指定を常に持ち、
  回転は今と同じ条件（表示用画像がある Drive の写真）で一覧・検索の両方で持つ。
- R10（必須）: カードの情報の優先順位を見直す。一覧・検索のどちらでも、位置のある写真は地名を主役にし、由来
  （EXIF・Drive・推定・手動）をタグで添える。位置のない写真は「次に何をするか」を主役にする（AI 候補があればその地名、
  無ければ近い時刻の位置、どちらも無ければ「手がかりなし」）。このため検索 API と一覧 API のどのフィルタでも、
  位置のない写真に AI 候補と近い時刻の位置を付ける。推定の段階窓（`infer_bucket`）は推定の写真だけに出す。
- R11（必須）: 検索結果のビューア（拡大表示・前後移動）と場面ごとの折りたたみは今の機能を失わない。
- R12（あると良い）: 検索結果の写真にも、一覧と同じ地名・由来のタグを出す。

### 設定タブ

- R13（必須）: 起動時に読み込んだ設定を、「起動引数 / 環境変数 / 既定 / AI 設定 JSON」の出どころつきで表示する。
  対象は [設定リファレンス](../reference/configuration.md) の「Rust が読む環境変数」の**全項目**（値が既定でも出す）と、
  AI 設定 JSON の全項目（用途ごとの送り先・モデル・サービス ID・クラウド許可・hidden の扱い・日の上限・認証ファイルの
  パスと有無・project・region、LAN の入口、embedding の空間の識別）。鍵のパスを含めて**設定どおりの値**で出す
  （2026-10-30 のユーザーの決定。「設定項目の全量が分かるようにしたい」）。
- R14（必須）: 出さないのは、鍵・認証ファイルの**中身**とトークン（そもそも設定が持たない）、内部の値
  （`embedding_contract`・`config_hash`）だけ。ファイルの項目は有無（と AI 設定 JSON の更新日時）を添える。
  ログ・`ai-jobs status`・状況 API の「モデル名・region・パス・URL を出さない」決まりは**変えない**。この API だけを
  意図した例外にし、文書とコードのコメントに例外を書く。設定タブの先頭に「鍵のパス・接続先・連絡先が含まれるので
  画面を共有しない」と案内を出す。
- R15（必須）: 設定ファイルの一覧（AI 設定 JSON のパス・読み込み状態・更新日時、Drive の鍵のパスと有無、順位モデルの
  パスと有無）と、「この画面は読み取り専用。変えるには環境ファイルと AI 設定 JSON を編集して再起動」の案内を出す。
- R16（あると良い）: クラウドの用途に「今日（UTC）の送信数 / 日の上限」を出す。
- R17（あると良い）: 起動からの経過時間とバイナリの版（`geoframe --version` と同じ）を出す。

### 旅行ブログの無効化

- R18（必須）: 環境変数 `GEOFRAME_BLOG`（既定 `0`＝無効）で旅行ブログを有効/無効にする。無効のとき
  `/api/blog/` 配下の GET と、`POST /api/blog/save`・`/api/blog/export` は 404（それ以外の POST は今までどおり 403）。
  ページ（`/blog-admin`）は R2 のとおり管理画面へ導く。有効のときは今と同じ画面・API が動く。
- R19（必須）: コード（`blog.rs`・`blog_write.rs`・`blog_export.html`・`post.rs` の経路）、埋め込みの旅程、
  データディレクトリの下書き・書き出しは消さない。
- R20（必須）: 設定リファレンスに `GEOFRAME_BLOG` を載せる（`env_reference` の試験が照合する）。デプロイの文書に
  「新しいバイナリへ更新した次回の起動から無効になる。戻すには `=1`」を書く。

### 安全・互換

- R21（必須）: 認証が無い前提の防御（Host 検査、JSON の Content-Type と Origin による CSRF 対策、`INGEST=0` での
  書き込み API の 503）を変えない。新しい読み取り API は GET のみ。
- R22（必須）: `GET /api/v1/photos`・`/derivatives/` の契約（miharashi）を変えない。
- R23（必須）: `cargo test`（画面の描画試験を含む）と clippy（`-D warnings`）が通る。

## 受け入れ条件

- AC1（R1, R3）: `/`・`/admin` を開くと「状況 / 写真」（PR ③ 後は 3 つ）のタブが見え、旅行ブログのリンクが無い。
  HTML と JS に `server.py`・`handlers.py`・`loc_suggest.py`・「表示画面」の文字列が無い（試験で grep）。
- AC2（R2）: `GEOFRAME_BLOG` 未設定で `/blog-admin` が管理画面の HTML、`=1` で旅行ブログの HTML。PR ② 以降、
  `/ai-search` は管理画面の HTML で、開くと「写真」タブが選ばれ検索欄にフォーカスが当たる（描画試験）。
  いずれも 404 にならない。
- AC3（R4）: 状況タブの AI 運用の描画試験（`web/tests/admin_ai_ops_render.mjs`）が、検証内容を変えずに通る。各パネルが
  今と同じキーを描くことは検証環境で目視。
- AC4（R6）: チップ 7 種の件数が `GET /api/admin/status` の `db.filters` と一致し、`db.filters` の各値が
  `GET /api/admin/photos?filter=<f>` の `total` と一致する（結合試験）。チップを押すと一覧が絞られ、ページが 1 に戻る
  （描画試験）。
- AC5（R7, R8）: 描画試験で、検索 API の実際の応答（503 `AI検索は無効化されています`・503 接続不可・429・400
  `bad_params`）のそれぞれで、検索欄の下に決めた日本語の文言（400 は「検索語は 300 文字以内で入力してください」）が出て
  一覧が残る。成功で検索結果に切り替わり、閉じると直前のフィルタとページで一覧を読み直す。
  「AI おすすめ」は検索語なしの検索と同じ要求を出す。
- AC6（R9, R10）: 描画試験で、一覧・検索の両方のカードから ★・除外・位置・（条件を満たす写真の）回転が操作でき、
  ★を押すと `POST /api/admin/setflag` が呼ばれ、応答で同じ写真の全カードとビューアが更新される。合成データ 7 通り
  （位置あり / 候補あり / ヒントあり / 手がかりなし / 推定 / 検索結果の位置あり / 検索結果の候補あり）で 1 行目と
  タグが規則どおり。結合試験で検索 API の写真に `source`・`hint`・`suggest` が付く。
- AC7（R11）: 検索結果の写真を開くと拡大表示され、前後に移動でき、場面の折りたたみが今と同じに動く（検証環境で
  目視。前後の順序は描画試験）。
- AC8（R13, R14）: 単体試験で、検査に通る形の目印（鍵のパス・`local_base_url`・`space_id` ほか空間の識別・`service_id`・
  `TILE_UA`・`project`・`DRIVE_FOLDER`・`RANK_MODEL` ほかのパス・`ALLOWED_HOSTS`）と、鍵のパスが指す合成ファイルの中身
  （`SECRET-mark`）を入れた設定から作った `GET /api/admin/config` の応答に、`items` の全項目があり、目印が**すべて値として
  含まれ**、鍵の中身が含まれない。`Config` の `Debug`・起動ログの要約には目印も鍵の中身もモデル名・region も含まれない。
  結合試験で本文に鍵の中身が無い。`source` が `arg/env/default` の規則どおり。項目の列挙に追加漏れがあると試験が落ちる。
- AC9（R15）: 結合試験で `GET /api/admin/config` が 200、`Cache-Control: no-store`、HEAD・POST・似た名前のパスは 403、
  `INGEST=0` でも 200。描画試験で設定タブに読み取り専用の案内と全項目が描かれる。
- AC10（R18〜R20）: `GEOFRAME_BLOG` 未設定で `/api/blog/trips` ほか GET 4 本と `POST /api/blog/save`・`export` が 404。
  無効時は CSRF 違反でも `INGEST=0` でも 404（404 ＞ 403 ＞ 503）。`=1` で今までどおり。`env_reference` の試験が通る。
- AC11（R21〜R23）: 既存の試験がすべて通り、`cargo clippy --all-targets -- -D warnings` が通る。
  `/api/v1/photos` の契約試験に変更が無い。

## 制約

- 技術: Rust（axum）＋素の JavaScript。静的ファイルは `build.rs` でバイナリに埋め込む。描画試験は Node で動かし、
  CI では Node 必須（runner に同梱。`package.json` は置かない）。
- 設定は起動時に読む。実行中の変更・再読込は作らない。
- PR は目的ごとに 3 本（下の実装の順番）。② と ③ は ① に依存する。
- 本番機でビルド・試験はしてよいが、デプロイ・サービス操作・本番 DB への接続はしない。検証は合成データと
  `cargo test` で行い、必要なら検証環境（LXC）で目視する。
- 家庭 LAN の IP・ホスト名・鍵の内容を文書・コード・PR に書かない。

## 実装の順番（PR の分け方）

1. **PR ①**: 「状況 / 写真」の 2 タブ、チップと件数、「要対応」、一覧側のカードの見直し（全フィルタの近い時刻の位置を含む）、
   `GEOFRAME_BLOG` フラグ、古い記述の掃除、起動の整理と描画試験の土台（R1 の一部、R2 の `/blog-admin`、R3〜R6、
   R10 の一覧側、R18〜R20）。`/ai-search` ページとそこへのリンクは残す。
2. **PR ②**: 写真タブへの AI 検索の統合とカードの統一、`/ai-search` を管理画面へ、AI 検索ページの削除
   （R2 の `/ai-search`、R7〜R9、R10 の検索側、R11〜R12）。
3. **PR ③**: 設定タブと `GET /api/admin/config`（R1 の設定タブ、R13〜R17）。

各 PR は単独でマージできる。① は ②③ のマージ前なら単独で戻せる。②③ のマージ後に ① を戻すには ②③ を先に戻す。

## 決まっていないこと

- （決定済み 2026-10-30）設定タブは鍵のパスを含めて全項目を値で出す。写真タブとカードのモックアップは承認前に見せる。

次の 3 点は設計で決めた（[design.md](design.md) の方針）: チップの件数は `GET /api/admin/status` の `db.filters`、
`/blog-admin`・`/ai-search` は転送ではなく同じ HTML、今日の送信数は `GET /api/admin/config` に含める。
