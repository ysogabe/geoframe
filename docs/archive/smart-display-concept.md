## 1. コンセプト

**「自分の写真が、その土地のデータと一緒に生きているデジタルフォトフレーム」**

壁のディスプレイに、ダークトーンのサイバーな日本地図が常時表示される。一定間隔で地図が写真の撮影地点へフライトし、ネオンのマーカーがパルスし、写真がHUD風フレームで浮かび上がる。写真の脇には撮影地点のGIS情報（標高、用途地域、地価、浸水想定、人口メッシュ…）がデータフィードとして流れる。ただのスライドショーではなく「旅の記録 × 国土データ」の演出装置。

## 2. UXモード（画面状態）

1. **AMBIENT / PHOTO JOURNEY（基本モード）**: 写真の撮影地点を地図が自動巡回。写真カード＋位置HUD＋GIS属性フィード。夜間は輝度を落とすナイトモード
2. **AREA INTEL（地点深掘り）**: 1枚の写真の地点に留まり、レイヤ（用途地域/ハザード/人口）を順にトグルしながら属性をアニメーション表示
3. **INTERACTIVE（将来）**: タッチ/音声で「この写真の場所どんなところ？」→ AI（MCPレイヤ）が解説

## 3. ハードウェア

- **Raspberry Pi 5 (8GB) 推奨**。MapLibre GL（WebGL）常時描画のため。Pi 4はズームアニメーションでフレーム落ちの懸念 → 実機検証項目
- ディスプレイ: 縦置き/横置き両対応のレイアウトにしておく（壁掛けは縦が映える）
- OS: Raspberry Pi OS + Chromium キオスクモード（`chromium --kiosk`）+ 自動起動・自動復帰
- **技術スタックをWeb（HTML/JS）に統一する意義**: PCブラウザ＝開発環境、Pi＝本番環境が同一コードになる

## 4. アーキテクチャ（段階設計）

```
[Phase 0: 完了]  ブラウザ単体 index.html（モックデータ内蔵）
[Phase 1: 完了]  Pi上のローカルサーバー（app/server.py）
                   ├─ 標準ライブラリの http.server（SimpleHTTPRequestHandler /
                   │   ThreadingHTTPServer）のみで実装。FastAPI等の外部Webフレーム
                   │   ワークは不使用
```

## 5. APIキー不使用でどこまでできるか（Phase 0-1の現実解）

**かなりできる。** 以下はすべて無認証・無償:

- **地理院タイル**（背景地図）: `https://cyberjapandata.gsi.go.jp/xyz/pale/{z}/{x}/{y}.png` 等。CSSフィルタ（invert + hue-rotate）でダーク/サイバー化するのが最速。地理院ベクトルタイルで本格ダークスタイルも可
- **地理院 標高API・逆ジオコーダ**: 写真地点の標高・市区町村名を無認証で取得（MCPサーバー自身も同じ地理院ジオコーダを使っている）
- **国土数値情報ダウンロードサービス**: MLITの30APIとほぼ同系統のデータ（浸水想定・用途地域・学校・駅等）が**ファイルとして無償ダウンロード可**。よく見る地域分だけGeoJSON化してPiに同梱すれば、APIキーなしで「実データ」の演出ができる
- 地価公示は国交省のオープンデータ（CSV）でも取得可

→ **Phase 2着手済み**: 不動産情報ライブラリAPIキーを取得し、`GEOFRAME_MLIT_KEY` 環境変数（`app/.env` で設定）経由でサーバーが実データを取得する形で稼働中。

## 6. Google Photos連携の制約（忖度なしの注意点）

2025-03-31のAPI変更で、**Library APIによる「ライブラリ全体の読み取り」は廃止**。サードパーティアプリがアクセスできるのは(a)そのアプリが作成したメディア、(b)ユーザーが**Picker APIで明示的に選択した**メディアのみ。つまり「Google Photosに写真を上げたら自動で全部ディスプレイに出る」は公式には不可能。

現実的な選択肢:

- **案A: Picker API + Piローカルキャッシュ**（公式・推奨）: スマホでアルバム/写真を選択 → PiがダウンロードしてEXIF処理・保存。新しい写真を足すときだけ選択操作が要る。baseUrlは約60分で失効するため**必ずローカル保存**する設計
- **案B: スマホ→Pi直接同期**（Syncthing / PhotoSync）: Google Photosを経由せず確実・全自動。ただし「Google Photos連携」という要件からは外れる
- 案C: 共有アルバムのスクレイピング — 非公式で脆く、規約リスクあり。**非推奨**

提案: Phase 1は案Aを本線、案Bを保険として両対応（どちらも最終的に「Piのphotos/フォルダにファイルが入る」設計に収斂するので、パイプラインは共通化できる）。

**実装結果: 案A・案Bどちらでもなく「Drive直接参照（サービスアカウント）」を採用。** 案Aは新しい写真を足すたびに都度の選択操作が要る、案Bはそもそも「Google Photos連携」という要件から外れる、という当初の懸念に対し、Googleサービスアカウント（`drive.readonly`スコープ）でDriveの`GeoFrame`フォルダを直接参照するという第三の道を採ることで両方の懸念を解消した。Drive API v3の一覧取得だけで`imageMediaMetadata`（撮影時刻・GPS）を取得できるためダウンロード無しに索引化でき、表示に使う写真だけをその都度2560px JPEGへ変換して`derivatives/`に保存する（オリジナルはローカルに保持せずDriveにのみ存在）。選択操作なし・Google Photos API側の制約（Picker APIのbaseUrl失効など）も受けない構成に落ち着いた。詳細な実装フローは `拡張コンテンツ検討_Google連携と追加表示.md` を参照。

## 7. ビジュアル演出の設計要素（Phase 0で検証するもの）

- ダーク反転させた地理院タイル＋グリッド/スキャンライン/ビネットのオーバーレイ
- 写真地点への `flyTo` カメラワーク（ズームアウト→巡航→ズームイン）
- ネオンパルスマーカー、写真カードのグリッチイン、HUDコーナーブラケット
- 座標・標高・時刻のモノスペースHUD、属性値のカウントアップアニメーション
- GISレイヤの半透明ネオンポリゴン（用途地域=シアン、浸水=マゼンタ等の色言語）
